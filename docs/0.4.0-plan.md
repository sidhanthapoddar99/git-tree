# Git Tree 0.4.0 — a Rust engine and a virtual graph

0.4.0 makes Git Tree fast on every platform and light on memory. It has two halves, built in parallel:

1. **A Rust engine** reads the repository in-process with gitoxide (`gix`), instead of starting a `git` process for each read.
2. **A virtual graph** in the webview draws only the rows on screen, instead of every loaded commit.

## Why both

- **Reads.** Each `git` spawn costs about 2 ms on Linux, 5–10 ms on macOS and 40–70 ms on Windows. Opening the view spawns several, and Commit Details spawns more. The Rust fork of Git Graph (`neophack/vscode-git-graph-rs`) measured a 4–5× faster view load, and 10–400× faster single reads, on Windows. On Linux the gain is smaller, because spawns are cheap there.
- **Drawing.** The webview builds a table row and SVG for every loaded commit: about 60 ms for 300 commits, 240 ms for 2,000, 520 ms for 5,000. That cost grows with the history on every platform. Drawing only the visible rows makes it flat.

## Decisions

| Decision | Choice | Why |
| --- | --- | --- |
| How Rust runs | A native Node module built with napi-rs, loaded into the extension host | Calls cost microseconds, with no process or protocol. The Rust fork proves it works. WASM can't run `git`, and gix in WASM is slower. A separate binary adds a protocol and a process. |
| What the engine does | Reads only: refs, the commit log, worktrees, commit details, diffs, files, config, tags | Writes go through the `git` CLI, so hooks, credentials and the user's settings behave as in a terminal. |
| `git status` | Stays on the `git` CLI | Git's status handles submodules, fsmonitor and sparse checkouts. A wrong "clean" is worse than a slower answer. |
| When the engine isn't sure | It returns `Unsupported`, and the TypeScript side runs the existing `git` CLI read | A wrong answer that looks right is worse than a slower right one. The CLI read is the reference, so it isn't a second copy. |
| Correctness | Differential tests: each engine read is compared with the CLI read on the same repositories | The CLI output is what users see today. |
| Graph layout | Stays in the webview | It takes one pass over the commits, a few ms. Moving it would only move the data. |
| Drawing | Virtual rows: only the rows in view, plus a margin, exist in the DOM; the graph is drawn for that window only | The drawing cost stops growing with the history. |
| Packaging | One `.vsix` per platform (`vsce package --target`), built in CI; a universal `.vsix` without the engine runs on the CLI | The Marketplace serves each user the right package. Platforms without a build still work. |
| Release profile | `opt-level = 3`, `lto = "fat"`, `codegen-units = 1`, `strip = true`, `panic = "unwind"` | Speed first. `unwind` lets napi turn a panic into a JavaScript error instead of crashing the extension host. |
| Versions | 0.4.0 when both halves land | A minor version: new engine, same settings and workflows. |
| Git version | 2.31 or later, required; older Git gets an error saying to upgrade | Decided by Sid: no fallback for old Git. 2.31 is when `git worktree list --porcelain` gained the fields the engine reproduces. |
| Linux builds | Built against glibc 2.28 with cargo-zigbuild | Visual Studio Code supports glibc 2.28 and later, and its Snap build runs on glibc 2.31. A module built against a newer glibc fails to load there. |

## Phases

Three releases, each measured against the one before. Each commit that changes performance says so in its message, with before and after numbers, so the history records what every change gained.

**0.4.0**

1. **Engine, view load** (done). `native/` workspace, `getRepoInfo`, `getRefs`, the commit log page, worktrees. TypeScript loader with CLI fallback. Differential tests and a benchmark script.
2. **Virtual graph** (done). Virtual rows and windowed graph drawing, with find, keyboard navigation, scroll-to-commit and Load More still working.
3. **Git 2.31 or later**, and Linux builds against glibc 2.28.
4. **Packaging and release.** Per-platform builds in GitHub Actions, the universal fallback package, release 0.4.0.

**0.4.1: the details reads.** Commit details, comparison, file content, config, tag details, remote URL and commit subject through the engine, and Git's incremental history walk, so a full log is never slower than `git`.

**0.4.2: fewer crossings and less data.** The same small payloads will travel over SSH for remote worktrees (0.5.0), so they have to be lean now:
   - **One crossing per view load.** Phase 1 makes six engine calls (branches, remotes, stashes, worktrees, refs, log), each a JSON string encoded in Rust and parsed in TypeScript. One `viewLoad` call returns them together.
   - **Only the fields the view uses**, with each string sent once: commits refer to authors and refs by index into shared tables, and hashes travel once.
   - **Deltas on refresh.** The engine keeps the last answer's ref tips and worktree HEADs per repository. A refresh returns only what changed, plus a token for the next refresh, and the webview patches its rows instead of reloading them.
   - **The webview gets the same compact form**, so the extension doesn't expand it to full objects before posting it.
   - **Measure each step**: bytes crossing Rust→TypeScript and extension→webview, and time, against 0.4.1.

## Targets for 0.4.0

Measured on Linux against 0.3.4, on the demo repository and a 6,750-commit repository:

- View load: faster than 0.3.4, and never slower.
- Drawing 5,000 loaded commits: under 100 ms, from about 520 ms.
- Memory in the webview with 5,000 loaded commits: lower than 0.3.4.
- No visible difference in what the graph shows: the differential tests pass.

Windows and macOS gains are expected from the spawn costs above, but this machine can't measure them.

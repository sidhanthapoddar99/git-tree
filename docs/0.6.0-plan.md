# Git Tree 0.6.0 — remote hosts in Repository Settings

0.6.0 makes the remote hosts of 0.5.0 manageable from Repository Settings, the way remotes already are. People can add a host from their SSH aliases, pick the repository's folder on the server by browsing it, create a new repository there, and run Git on the server with their SSH agent forwarded. It also adds a filter that hides a host, a button that copies the instruction for coding agents, and a redesign of the whole Repository Settings panel. The graph itself doesn't change.

## Decisions

| Decision | Choice | Why |
| --- | --- | --- |
| Where hosts are managed | A *Remote Hosts* section in Repository Settings, under *Remote Configuration*, with one row per host: its state, alias, path, options and actions. The *Add Remote Host...* command stays | Remotes are managed there, and hosts are the same kind of thing. The command keeps working for people who use the palette. |
| The contract | New request and response messages in `src/types.ts`: `loadRemoteHosts`, `browseRemoteHost`, `checkRemoteHost`, `saveRemoteHost`, `createRemoteHostRepository`, `removeRemoteHost` and `runRemoteHostGit` | One message per action, like the other settings actions, so each has one handler and one test. |
| Loading the section | `loadRemoteHosts` answers from what `RemoteHosts` already knows (`getHosts`), plus the SSH aliases and the agent instruction. It never waits for the network | Opening settings must be instant even when a server is down. A host's state updates when its own refresh finishes. |
| SSH aliases | Read from `~/.ssh/config` and the files its `Include` lines name (with `~`, relative paths and globs, as `ssh_config(5)` reads them, to a depth of 16). Each literal `Host` alias is offered, with that block's `HostName` and `User` as a hint. The files are only read | The issue asks for the aliases to appear by themselves. Many people keep hosts in included files. The hint tells two aliases of one machine apart. A typed alias that isn't in the files is still allowed, because `ssh` may know it from a file Git Tree doesn't read. |
| Browsing the server | `browseRemoteHost` runs a fixed script over the shared connection: it changes to the asked path (or the home folder), prints its physical path, and lists the folders in it, each marked *repository* (it has a `.git` folder), *worktree* (a `.git` file) or *folder*. Names are NUL-separated, and at most 2,000 are listed | One round trip per folder, about 16 ms on a shared connection. The script is fixed and the path is a quoted argument, as for the status call. A `.git` file means a linked worktree or a submodule, which can't be a host's main worktree, so the browser marks it apart. The cap keeps a huge folder from flooding the view. |
| Adding an existing repository | The path must be a repository's main worktree, and it must pass the 0.5.0 checks (connection, then same project) before the file is written | The same rules as the command, so both write only hosts that work. |
| Creating a repository | The folder must be missing or empty. *Clone*: the server runs `git clone <url> <path>`, where the URL is one of this repository's remotes. *Push*: the server runs `git init` and points `HEAD` at this repository's current branch, then this machine pushes its branches with `receive.denyCurrentBranch=updateInstead` for that one push, which checks the branch out on the server. After either, the host is added as above | Clone suits a repository on GitHub, which the server reaches with the forwarded agent. Push suits a repository the server can't reach. `updateInstead` is set only on the receiving command, so the server's config isn't changed. |
| Agent forwarding | A host's optional `forwardAgent: true` key (default false). Only the commands that leave the server use it: the clone, and the server's fetch, pull and push. Those run on their own connection, `ssh -A` without connection sharing. The status call, browsing and the worktree actions never forward the agent | Forwarding lets anyone with root on the server use the agent while it's forwarded, so it lasts only for the command that needs it. A shared connection would either carry it for 2 minutes after its last use or not at all, depending on which call opened it. The extra handshake costs about 0.2 s on a command that takes seconds anyway. |
| Git on the server | `runRemoteHostGit` runs `git fetch --all --prune`, `git pull --ff-only`, or `git push` in one of the host's worktrees, with `GIT_TERMINAL_PROMPT=0`, then refreshes the host. The Remote Hosts row offers them for the main worktree, and the worktree menu in the graph for each server worktree | The issue's "sync and manage". `--ff-only` never makes a merge commit on the server by surprise. No terminal prompt, so a missing credential is an error instead of a hang. |
| The config format | Still version 1, with the new optional key `forwardAgent`. Git Tree writes `worktrees` only when it's false, and `forwardAgent` only when it's true | The keys are optional, so files that 0.5.0 wrote still mean the same. 0.5.0 reports the new key as an error on its line instead of guessing, which is the rule. |
| Editing a host | `saveRemoteHost` with the old name replaces that entry in place, keeping comments and order. A changed alias or path is checked as an add is. A renamed host keeps its fetch consent, and its old refs are deleted | One writer for add and edit, so they can't drift. The rename keeps what the user already allowed. |
| The host filter | `hideHosts` in each repository's state, next to `hideRemotes`. A hidden host's worktrees, *Uncommitted Changes* rows, branches and start points leave the view, and a view's refresh skips its SSH call. Repository Settings toggles it per host. It goes in the exported repository settings file like `hideRemotes` | The same model as hidden remotes, so it's one rule to learn. Skipping the call makes a hidden host cost nothing. |
| The agent instruction | One string in `src/remoteHosts/agentInstruction.ts`. `loadRemoteHosts` sends it, the *Copy* button copies it through the existing `copyToClipboard` message, and a test checks that `docs/remote-hosts-for-agents.md` holds the same block | One source, so the copied text and the docs can't drift. |
| The Repository Settings redesign | Each section is a card with a title, a one-line description and its actions in its header. Lists are rows with icon buttons instead of tables. Switches replace bare checkboxes. Everything uses the VS Code theme variables, so light, dark and high-contrast themes all work | The user asked for a newer settings UI. Theme variables make it look native in every theme without a color of its own. |
| The add-host flow | A form inside the Remote Hosts card, in three steps: the alias (from the list, or typed), *Add existing* or *Create new*, then the folder from the server browser. The name, *Include the server's worktrees* and *Forward my SSH agent* come last, then *Check* and *Add* | A dialog can't hold a folder browser. Steps in the card keep the page in place. |
| Version | 0.6.0 | A minor version: new features, no change to existing settings or files. |

## Measure

On the test server, with and without a shared connection: one `browseRemoteHost` call, `loadRemoteHosts` with two hosts, and a server fetch with and without agent forwarding. And the view load with a hidden host against a shown one, which must not grow.

## As built

Where 0.6.0 differs from the decisions above, and why:

- **`loadRemoteHosts` reads the config file**, not only what `RemoteHosts` already holds, so the section isn't empty the first time it opens. It still never waits for a server.
- **No SSH call forwards the agent unless the host asks.** Every call except the terminal passes `-o ForwardAgent=no`, because a `ForwardAgent yes` in the user's SSH configuration would otherwise forward it on status calls, browsing and fetches.
- **Adding a host checks that the path is the main worktree** (`git rev-parse --git-common-dir` is `<path>/.git`). 0.5.0 accepted a linked worktree or a folder inside a repository, which drew the wrong rows. The palette command gets the same check. The agent instruction now uses that check too.
- **A clone refuses some remote URLs**: paths and `file://` URLs on this machine, which mean nothing on the server, and URLs with a password in them, which would land in the server's config.
- **A failed push leaves the empty repository on the server**, and the error says so. Git Tree deletes nothing on a server.
- **`Include` paths with `%` tokens or `${VAR}`** aren't expanded, so they match no file. Aliases from a file included inside a `Host` block are still listed.
- **Browsing finds the parent with `dirname "$(pwd -P)"`**, not `cd ..`, which goes back up through a symbolic link. When it stops at 2,000 folders it says so (`truncated`), and the browser asks the user to type a path.
- **Repo info keeps every host's state**, hidden or not, so Repository Settings can show them. Only a hidden host's worktrees and branches leave the view.
- **The refresh interval also skips a hidden host**, when every saved view of the repository hides it, so hiding a host stops its SSH calls everywhere.
- **The panel is 460 px wide**, not 400, so a host row and the folder browser fit.
- **Push asks first**, in the row and in the worktree menu. Fetch and pull don't, because they change nothing the user can't undo with another pull.
- **Responses carry no request ID**, so the webview matches each to its request: one listing and one save at a time, a check by alias and path, and a Git command by host and action.
- **The tests never use the user's SSH agent.** The test wrapper reads a private agent's socket from a file and unsets `SSH_AUTH_SOCK` otherwise. The forwarding tests clone from `dev@localhost` inside the test container, which works only if the agent is forwarded.

Measured on the test server (loopback, median of 9): listing a folder takes 17–26 ms with a shared connection and 162–165 ms without; a fetch on the server 58 ms, and 190–201 ms with the agent forwarded on its own connection. `loadRemoteHosts` with two hosts takes 0.1 ms. The view load with a hidden host was no slower than with it shown, within noise.

Not tested: forwarding to GitHub itself, Windows clients, and the panel inside VS Code. The panel was checked in Chromium with the real webview code and a fake extension, in light, dark and high-contrast themes.
